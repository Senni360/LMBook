# T3 Code UI reliability reference review

Status: bounded research completed 2026-09-14. This note uses the official
[pingdotgg/t3code repository](https://github.com/pingdotgg/t3code) only. It
borrows failure-prevention ideas, not visual treatment, colors, or product
features. Issue status and dates below are the repository state inspected on
2026-09-14. A report is evidence that the behavior was observed or diagnosed;
it is not evidence that every platform reproduces it. A fix is called merged
only where the issue or pull request explicitly shows that state.

The application review covered `src/main.tsx`,
`src/components/ActivityHistory.tsx`, `src/components/SourceSnapshotReader.tsx`,
`server/index.ts`, `server/jobs.ts`, `server/activity.ts`, and the related CSS.
No production code or automated tests were changed.

## Prioritized checklist

| Priority | T3 Code evidence and upstream state | When SenniBook could encounter it | Existing protection or manual check | Planned fix if warranted |
| --- | --- | --- | --- | --- |
| P0 | **Restart loses in-memory progress and leaves work stuck.** [Issue #6560](https://github.com/pingdotgg/t3code/issues/6560) (opened 2026-08-14, closed with [PR #7719](https://github.com/pingdotgg/t3code/pull/7719), merged 2026-08-20) documents a backlog discarded on restart: provider work had completed, while the UI remained in `starting` with no startup reconciliation. | A generation, OCR, or transcription is running while the Electron process, backend child, or machine is closed and reopened. The visible banner could disagree with persisted episode/source state. | Generation activity is durable in SQLite; startup calls `reconcileInterruptedActivities()` and converts persisted `running` rows to `interrupted`. The live `jobs` map is process-local, and the renderer learns about it only from `/status`; this is a good guard but not proof that every restart path reconciles the visible state. **Manual check:** start each long operation, quit/reopen at several progress points, confirm no permanent spinner, the saved partial work remains usable, and the history row is terminal with an actionable retry path. | No implementation change is justified by the upstream report alone. If the manual check finds a mismatch, make operation recovery authoritative from persisted state and show one explicit terminal state before considering retry. |
| P0 | **Stop/cancel needs an escape path and must be state-gated.** [Issue #2234](https://github.com/pingdotgg/t3code/issues/2234) (opened 2026-04-20, closed as not planned) reported that a running thread could not be stopped. T3 retained and merged [PR #4308](https://github.com/pingdotgg/t3code/pull/4308) on 2026-09-07: a configurable `thread.stop` command, no default shortcut, only interrupts a running thread, ignores key repeat, and does not consume the key when stopping is unavailable. | SenniBook exposes a mouse-only `Stop` button in the job banner. A long script/audio job, or one that is heading the wrong way, may be hard to stop when focus is in an editor or the window is being used from the keyboard. Repeated clicks, cancellation during a transition, and cancellation after the job already ended are also state races. | `/api/notebooks/:id/cancel` aborts the in-memory controller; generation checks the signal between chapters/segments and saves completed work. The renderer disables most editing while `job` is true. **Manual check:** cancel before the first provider response, between chapters, during audio, twice, after completion, and while changing tabs; verify the button returns to idle, the activity row is `cancelled` or `failed` with truthful text, and completed work remains resumable. | Consider a keyboard stop command only after the manual check establishes a real need. If added, reuse the existing cancel path, gate it on an active job, ignore repeats, and leave it unbound by default until the shortcut semantics are decided. |
| P0 | **Oversized input crossed the server boundary and exposed an internal error.** [Issue #6105](https://github.com/pingdotgg/t3code/issues/6105) (opened 2026-08-11, closed with [PR #6602](https://github.com/pingdotgg/t3code/pull/6602), merged 2026-08-15) reports a 120,001+ character composer send producing a provider validation stack trace. The merged fix validates at final submission, keeps the draft editable, reports the exact overage, and permits the exact boundary. | The chat field already has a 6,000-character limit, but the transcript editor has no `maxLength` and server `turnSchema.text` accepts at most 12,000 characters. A pasted or generated oversized `A:`/`B:` turn can fail only after editing, with the user at risk of losing the intended correction or seeing a generic error. Goal/source/settings fields have separate limits that should remain aligned with their server schemas. | `server/index.ts` validates chat at 6,000; `server/jobs.ts` validates transcript turns at 12,000; source and bundle schemas also bound text. **Manual check:** submit one value just over every user-facing boundary and one exactly at it; confirm the draft remains intact, the message names the limit, no raw validation detail appears, and a corrected retry succeeds. | If the check exposes a gap, add client-side boundary feedback at the actual save/submit boundary and preserve the draft on rejection. Keep the server schema authoritative; do not silently truncate learning text. |
| P1 | **Large histories can turn rendering or hydration into a crash.** [Issue #5351](https://github.com/pingdotgg/t3code/issues/5351) (opened 2026-08-04, closed via the linked [PR #6153](https://github.com/pingdotgg/t3code/pull/6153)) recorded 3.4–3.6 GiB backend memory while loading every activity payload. The later [Issue #8648](https://github.com/pingdotgg/t3code/issues/8648) shows that bounded readers in 0.0.35 did not eliminate all long-uptime OOM paths, so the fix is not a general guarantee. | `getNotebook` returns the full notebook, including source text, messages, episodes, turns, and context. A large imported course pack combined with many generated chapters or chat answers could make reopening, switching notebooks, or rendering a source snapshot expensive. | Imports and bundle restore have explicit file/text caps; `SourceSnapshotReader` uses a 65vh scroll region and wraps long text; `ActivityHistory` asks for a bounded recent list. There is no pagination or history eviction for the notebook object itself. **Manual check:** reopen a notebook near the supported source/text limits with several long episodes, switch tabs repeatedly, open a highlighted snapshot, and observe responsiveness, memory, and recovery after a backend restart. | Do not add a speculative virtualized history. If the check finds a real threshold, bound the read path first, preserve source provenance, and expose “load older” or an equivalent explicit state before changing retention. |
| P1 | **Streaming a long conversation can reparse all prior content on every delta.** [Issue #4074](https://github.com/pingdotgg/t3code/issues/4074) (opened 2026-07-17, closed 2026-09-11) measured about 76% CPU in a long chat versus 35% in a fresh chat and diagnosed O(n²) full-message Markdown reparsing. The repository's audit [Issue #9661](https://github.com/pingdotgg/t3code/issues/9661), opened 2026-09-04, lists this as W02; [PR #9677](https://github.com/pingdotgg/t3code/pull/9677) and the follow-up [#11193](https://github.com/pingdotgg/t3code/pull/11193), [#11196](https://github.com/pingdotgg/t3code/pull/11196), and [#11198](https://github.com/pingdotgg/t3code/pull/11198) are shown as merged. | SenniBook currently waits for a complete chat response before adding one message, so it does not have this exact token-delta loop. It still renders every saved chat message and every episode turn, and source snapshots render the entire saved text. Future streaming or very long notebooks could recreate the same cost. | Current plain-text rendering avoids Markdown highlighting work; `.messages` and `.source-snapshot-text` have bounded scroll regions, while transcript turns wrap long text. **Manual check:** measure a long chat/episode/source while switching tabs and scrolling; if streaming is later added, compare CPU and input latency with short and long histories and verify that scrolling remains usable. | No immediate change. If streaming is introduced or the manual check shows lag, render stable completed blocks/turns incrementally and keep the current text as the source of truth; avoid reparsing or remounting the whole history per update. |
| P1 | **A draft can be valid locally but fail only after dispatch, or draft work can be made expensive by persistence.** The T3 audit [Issue #9661](https://github.com/pingdotgg/t3code/issues/9661) lists W04 (“draft persistence serializes all draft data before its debounce”) and M5 (typing can synchronously serialize image-bearing drafts). The audit links [PR #9695](https://github.com/pingdotgg/t3code/pull/9695), merged 2026-09-04, for deferred composer serialization. | SenniBook’s `Chat` message, `Goals` entry text, and `Studio` script text are component-local state. Switching tabs or notebooks unmounts those components; a failed request preserves some state because clearing occurs after success, but a navigation/reload can discard unsaved text. | Chat has `maxLength={6000}` and clears only after `change` succeeds. Source/goal/settings schemas bound persisted values. There is no draft storage or navigation warning. **Manual check:** type a substantial question, goal list, or transcript; switch tabs/notebooks, trigger a provider failure, reload the desktop window, and attempt a save while a job is active. Record whether preservation matches the intended product behavior and whether typing remains responsive. | This is a product decision before implementation: if unsaved work must survive navigation, add scoped draft persistence with bounded data and clear ownership; if it should be ephemeral, warn before the action that would discard it. Do not persist every keystroke synchronously. |
| P2 | **A loading/retry state can be inferred from incomplete data and remain stuck.** [Issue #318](https://github.com/pingdotgg/t3code/issues/318) (opened 2026-03-07, closed with merged [PR #595](https://github.com/pingdotgg/t3code/pull/595) on 2026-03-10) describes a diff panel stuck on “Loading” when the checkpoint was not yet usable. The fix separated subscription delivery from checkpoint readiness and replaced missing placeholders rather than treating every present record as diffable. | SenniBook has several asynchronous states: source processing, OCR/transcription, provider generation, activity history, and source-reader navigation. A record can exist while its text/audio/cache is still unavailable, or a request can fail after the UI has entered a loading state. | `ActivityHistory` distinguishes loading, error, empty, and retry; source processing stores `pending`/`recognizing`/`transcribing`/`failed`; generation history has `running`, `cancelled`, `interrupted`, and `failed`. **Manual check:** delay or interrupt each operation, reopen the notebook, open history while loading, retry after a transient failure, and confirm every spinner has a terminal/error path and every retry does not duplicate work. | If a stuck state is found, model the missing distinction explicitly (for example, queued, temporarily unavailable, failed, ready) and make retry idempotent. Avoid using the presence of a database row as proof that its payload is usable. |
| P2 | **Overlays can be present but invisible because an ancestor clips them.** [Issue #4342](https://github.com/pingdotgg/t3code/issues/4342) (opened 2026-07-23, closed with merged [PR #4365](https://github.com/pingdotgg/t3code/pull/4365) on 2026-07-23) reports composer `$`, `/`, and `@` menus rendered outside the visible clipping region. The fix portaled the shared menu outside the clipping host. | SenniBook currently uses a native `<dialog>` for notebook creation and inline source/evidence readers rather than a composer popover. Future autocomplete, source actions, or mobile controls could be clipped by a scroll container or narrow desktop layout. | `create-dialog` sets a viewport-aware max width; source snapshot controls become full-width below 560px; long text uses `overflow-wrap:anywhere`, and the existing manual mobile check found no horizontal overflow. **Manual check:** at 390px and a narrow desktop width, open the create dialog, source reader, evidence links, and any future menu from inside a scrolling region; verify the control is visible, reachable by keyboard, and not cut off by an ancestor. | If a real overlay is clipped, change its positioning/portal boundary and add a manual regression check for the containing scroll context. Do not copy T3’s visual treatment. |

## Decisions and uncertainty

### SenniBook follow-through, 2026-09-14

The table records the reviewed baseline. Root reproduced unsent chat text disappearing when switching tabs in the earlier packaged app. The next preview adds bounded draft persistence for questions, pasted sources, goal lists and chapter-script edits, with source/goal types and separate chapter ownership. Serialization is deferred; navigation and page exit flush the last edit. Accepted requests clear only the matching submitted draft, including after a component remount; newer typing is preserved. Script save validation now names the offending turn and limit while keeping the editor open.

Manual Chromium workflows exercised tab changes, reloads, simulated provider failure, delayed acceptance after remount with and without newer typing, fast acceptance before the storage debounce, per-chapter script drafts, invalid long turns, and actual source/goal/script saves. These passed without renderer errors. Simulated quota failure kept current text and showed the persistence warning; disabling local storage did not prevent opening notebooks. A delayed notebook response cannot replace a later selection. Notebook navigation is independent of the mutation-busy gate, which previously ignored a second selection during loading. Field labels now remain stable when restored textarea text is present.

The provider-response delays above were controlled UI simulations, not real generation or educational validation. Existing independent live-provider checks are recorded in WORKLOG.md. No new automated test files were added; reusable regression coverage remains deferred to the owner's final sweep. Large-library performance and restart cases in the table remain open unless separately documented as exercised.

An independent targeted review caught shared-storage draft conflicts between browser tabs and deletion completing after a newer notebook selection. Root checked the corrections with two actual pages sharing browser storage and a delayed real DELETE against an isolated notebook. Autosave, acceptance, empty cleanup and discard preserve a foreign newer draft; the conflict message asks the learner to copy their local text before reopening the saved version. These guards are not an atomic multi-user synchronization protocol: localStorage has no compare-and-swap primitive. At 390px, a new editor action row initially clipped its first button even though the page reported no horizontal overflow. Wrapping the actions fixed it; button bounds and a rendered screenshot were checked. Page width alone is insufficient evidence of reachable controls.

The highest-value prevention work is state truthfulness: every long operation
needs a durable terminal state, a real cancel path, preserved user input on
rejection, and a retry that does not duplicate or silently discard work. T3’s
merged fixes support those principles, but their provider/session architecture
does not prove that the same failure exists in SenniBook.

No upstream release is treated as a universal fix. T3’s own performance audit
marks browser/device verification as excluded, and issue #8648 reports remaining
OOM paths after earlier hydration bounds. The SenniBook checks above therefore
remain manual acceptance checks until the application is exercised with large
realistic notebooks and interrupted operations. This review provides no
evidence of educational effectiveness.
