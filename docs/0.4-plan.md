# LMBook 0.4 — working milestone

Owner decision, 16 September 2026: adopt the recommended shared-vault direction, iterate on working versions of the whole app, and call the result 0.4 only when the owner considers it ready. Technical checks inform the decision; they do not substitute for the owner's product review. The owner then explicitly requested implementation. The first shared-vault workflow is implemented in the local 0.3.11 preview; [behavior, evidence and remaining boundaries](obsidian-vaults.md).

## Confirmed outcome

Connect an existing Obsidian vault so LMBook and Obsidian use the same files. Browse, edit and create notes from LMBook, and use selected notes for AI summaries and learning outputs. Preserve LMBook's independent operation for people without a vault. Current Ink work and UI fixes belong to this iteration effort.

The integrated editor is LMBook's own interface. Embedding the proprietary Obsidian app and running arbitrary Obsidian plugins are not promised by this decision. Specific plugin requirements remain open; see [the feasibility evidence](research/obsidian-feasibility.md).

## Proposed implementation sequence

Steps 1–3 now have a working preview: connection, Markdown editing/creation and recovery, selected-note snapshots, and reviewed AI summary drafts. Step 4 has only basic note-link resolution; full compatibility and whole-app refinement remain open. This does not mark 0.4 complete.

1. Connect/disconnect a chosen vault folder and browse its Markdown notes. Keep originals in place and leave Obsidian configuration untouched.
2. Read, edit and create notes, preserve unsupported syntax, and detect external edits. A conflict must offer a recoverable choice rather than silently overwrite either app's work.
3. Select vault notes for existing learning workflows and create generated notes in the vault. Preserve the exact source snapshot behind previously generated material. Let the learner inspect generated text before replacing any existing note.
4. Refine supported links, attachments, search and editor interactions against real vault examples. Identify required plugins individually instead of claiming universal compatibility.
5. Iterate on the whole experience from owner feedback. Keep unresolved defects and compatibility limits visible; check Windows and Mac behavior and the existing learning flows before release.

## Release gate

`release-policy.json` targets `0.4.0` and currently has `approvedVersion: null`. CI can build and verify iteration artifacts but cannot publish through the release workflow or release script. A merge or passing checks is not owner approval. Keep the gate closed until the owner explicitly says the release is ready.

After that decision: finish release notes, align the package version, record the approved target version, and run the existing all-platform build/verification/publication flow. Do not turn a review checkpoint into a release merely because a session ends. [Release mechanics](releasing.md) remain the operational reference.
