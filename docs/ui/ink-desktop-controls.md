# Ink controls and desktop chrome

Owner direction, 16 September 2026: application menus, the top bar, close controls and other exposed system styling should belong to Ink. Keep platform UI only where it serves the task. This supersedes the older preference to retain the Windows title bar. Use visual evaluation and preserve learning behavior throughout.

## Design decisions

- Keep the existing pen contours, readable type, white paper, blue focus and yellow emphasis. Do not introduce another visual theme.
- Use a quiet 40px draggable desktop bar. Its app menu, window controls and current notebook title share the app palette. Controls are outside drag regions. Windows keeps thick-frame resizing; macOS places close/minimize/maximize on the left and retains its system menu and close-to-background behavior.
- Dropdowns use customizable native selects (`appearance: base-select`). Their popovers, selected checks, hover states and opening caret are custom; labels, values, form serialization, keyboard selection, validation and top-layer placement remain browser-owned. Electron supports this. Browsers without support retain their usable native picker.
- Menus, confirmation dialogs and tooltips use the same paper border, small asymmetric corners, subtle shadow and short arrival. Menus do not slide in from a page-navigation direction. Hover, focus and selection remain distinct.
- Real audio elements retain chapter/source refs, events, seeking and saved positions. Shared custom transport, timeline, time and volume controls replace Chromium's media chrome. Range tracks and progress indicators follow Ink too.
- Confirmations use modal dialogs with a safe default, Escape cancellation and return focus. Active-work quit decisions are still enforced in the desktop main process. IPC uses a small action allowlist and validates the originating main frame. Request identifiers prevent a stale dialog response from answering a newer quit request.
- File open/save dialogs, the OS tray menu, the macOS global menu and emergency startup/crashed-renderer errors remain platform UI: they operate outside the page or must work when the page cannot. No replacement filesystem browser or clipboard permissions are introduced.
- Respect both the OS motion preference and LMBook's reduced-motion setting. High-contrast mode restores system borders/focus and native range rendering. Existing navigation direction and flashcard answer concealment remain independent of animations.

## Evidence and alternatives

The baseline exposed native select menus, native confirmations and audio players alongside Ink fields. Rebuilding every select as a JavaScript combobox would duplicate browser selection and validation behavior and add failure cases without improving the intended appearance. Chromium's [customizable selects](https://developer.chrome.com/blog/a-customizable-select) and [MDN's styling reference](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select) support using a native semantic substrate with custom presentation. Electron's [BrowserWindow documentation](https://www.electronjs.org/docs/latest/api/browser-window) defines the window state/action APIs; the renderer never receives a generic IPC bridge.

Native computer-use capture was unavailable (native pipe missing). Review uses Playwright screenshots of the browser and actual Electron window, with copied authored fixtures and silent WAV playback. No owner library or paid provider generation is used. These checks establish interface behavior, not learning effectiveness or owner preference approval.

## Evaluation record

Locally implemented and packaged as 0.3.9. Production build, all 38 existing tests and the existing isolated desktop startup/sandbox/persistence/restart check pass. Visual review caught and corrected the initial audio progress CSS specificity and inherited legacy player color. Browser confirmation cancellation returns focus to the invoking control. Real Electron maximize/restore and menu End/Escape navigation work. An authored active-job response exercised Stay and background choices without running generation. Mobile flashcard/picker layouts fit 390px without document overflow.

Final checks: the packaged Windows app passes the existing startup/sandbox/persistence/restart check. Its custom minimize, maximize/restore, full-screen, zoom and all three active-work quit choices were exercised with an authored status response. Safe dialog focus and Escape restoration pass. Select keyboard cancellation retains the previous value; End/Enter commits a choice. Sources, learning goals, audio, chat, flashcards and settings were reviewed at desktop/tablet/phone sizes (390, 700, 768 and 1440px), with no document overflow in the checked layouts. OS reduced motion, in-app reduced motion and forced colors were checked. Silent WAV playback, seeking, tooltip dismissal and section-to-section saved position were exercised; the latter exposed and fixed a metadata-listener remount edge case. No page errors were observed during the final browser pass. Local screenshots are in `.work/lmbook-custom-ui/.work/custom-ui/` from the root workspace. Physical drag/snap gestures and native Mac execution are not available on this Windows runner; Mac behavior needs the release matrix and hardware evaluation. Owner evaluation of the new visual balance remains open.
